# ADR-0030: Administration happens in the app; the Django admin is optional and read-only

- **Status:** Proposed (the maintainer's decisions of 2026-11-12, Q70–Q72, issue #53; accepted when the pull request of that phase merges)
- **Date:** 2026-11-13
- **Governs:** `apps/core/admin.py`, `apps/accounts/admin_site.py`, `apps/*/admin.py`, `config/urls.py`, `apps/accounts/management/commands/reset_mfa.py`, `apps/catalog/services.py`, `docs/design/admin-inventory.md`, `apps/organizations/services.py`, `apps/organizations/selectors/preview.py`, `apps/organizations/selectors/structure.py`, `apps/organizations/views/company_screens.py`, `apps/organizations/views/branch_screens.py`, `apps/organizations/structure_dialogs.py`, `apps/catalog/selectors.py`, `apps/catalog/unit_views.py`, `apps/catalog/unit_dialogs.py`, `apps/locations/services.py`, `apps/locations/selectors.py`, `apps/locations/views.py`, `apps/locations/dialogs.py`, `apps/locations/forms.py`, `apps/organizations/views/account_actions.py`, `apps/organizations/row_dialogs.py`

## Context

The Django admin was the master-data screen. Group administrators edited companies, joint-venture members, branches, warehouses and worksites (`org.manage`), categories and materials (`catalog.manage`) and suppliers (`supplier.manage`) there. The admin saved through the same services as the app (`ServiceBackedModelAdmin`), so generations, audit and deactivation rules applied. Everything else was read-only there, and nothing could be deleted. In production, Caddy lets only the addresses in `ADMIN_ALLOWED_CIDRS` reach it, and the admin site admits only platform operators and group administrators with session MFA.

That had three costs:

- A group administrator away from the allowlisted addresses could not open a branch or a warehouse.
- The admin is outside the app's gates: the design system, the phone layout, dialogs, accessibility and keyboard tests, translations and the access acceptance matrix.
- An editable admin is privileged surface that the checks have to police: `gmat.E005`, `lookup_allowed`, the refusal of inline saves.

Some work had no screen at all. Units of measure were seeded and read-only everywhere. A lost second factor needed `manage reset_mfa` on the server. A person's full name, required since ADR-0029, could not be corrected anywhere.

## Decision

1. **Everything a person administers has a screen in the app.** [`docs/design/admin-inventory.md`](../design/admin-inventory.md) classifies every model registered in the admin and every `manage` command, and maps the screens that are added: companies and joint-venture members, branches (incl. the managing branch, self-approval, the default warehouse and activity), warehouses, worksites' names and activity, units of measure, a person's name and the second-factor reset. The screens call the services that exist. A rule a screen needs that no service has is added to the service, never to the view. Deactivating or reactivating a company or branch, and changing a branch's managing branch, open a danger dialog that previews whose access changes. The service decides, and its refusal is shown in the dialog. *Implemented in M10.2:* the preview (`organizations.selectors.preview`) re-reads the access rules of `apps.access.context` (S1, S4, S8, S9) on the organization as it is and as it would be: the branches that leave or join a managing branch's scope or stop granting, the valid memberships and project assignments whose reach changes, the people who no longer reach any branch or project (by name, the first ten; the installation-wide catalog is left out of reach, so the dialog never claims a person loses it), and the open documents that make a deactivation refused. The dialog carries the `AccessState.org_generation` the preview was read at; `update_company` and `update_branch` take it as `seen_generation` and, under the `AccessState` lock and only when something changes, refuse a confirmation given on an organization that changed since (code `edited`: a 409 to the dialog, a flash without JavaScript). Membership and assignment changes do not move that counter, so the counts of people are a reading, not a promise. Self-approval gets a confirmation naming the self-decision rule (ADR-0014, ADR-0019). The structure screens live under `/org/structure/` in a new *Administration* menu category (ADR-0027).
2. **The admin is optional.** `DJANGO_ADMIN_ENABLED` turns it on; it is off by default in production and on in development and tests. While it is off, no admin URL exists and the prefix answers 404 like any unknown path. The admin app stays installed, so its system checks still run. While it is on, admission is unchanged (platform operators and group administrators, allauth login, session MFA, `lookup_allowed`, no deletes), and the deploy requires `ADMIN_ALLOWED_CIDRS` and refuses an open list. Without the admin, the deploy needs no allowlist.
3. **The admin is read-only for every model.** No `ModelAdmin` can add or change a record, whoever is signed in. Three checks make sure a future model cannot become editable again: a system check next to `gmat.E005`, a rule in `scripts/check_access_rules.py`, and a test that every registered model has a row in the inventory.
4. **A lost second factor is reset from the person's page** by an `org.manage` holder with session MFA, through `accounts.services.credentials.reset_user_mfa` as a session operation. A reason is required, and so is a tick that the person's identity was checked outside the application (stored in the audit payload). The effects are the command's: every factor and the recovery codes removed, every session ended, the owner told by email through the outbox (ADR-0024), audited as `user.mfa_reset` naming the administrator, and logged to `gmat.security`. Nobody resets their own factors (ADR-0022). A staff or superuser account is reset only by `manage reset_mfa` run by a superuser, which stays as the break-glass path. *Implemented in M10.4:* `reset_user_mfa` takes `identity_checked` (refused when false, also on the command line, `--identity-checked`) and an optional idempotency key (operation `user.mfa_reset`: a double tap resets once), refuses a staff or superuser account to any `SessionPrincipal`, a superuser's included, and writes the `gmat.security` line `mfa_reset_by_admin` (the account and the administrator, by id) after commit; the command never logged one before. The screen is an inline danger dialog of the person's page (`org:reset_mfa`), offered only while the person has an authenticator (`accounts.selectors.has_second_factor`), never on one's own page or a staff account's. A replay of the same form after the person enrolled again changes nothing; a new form resets again. The recovery replay handler of `user.mfa_reset` (ADR-0016) is unchanged: it reads only the account.
5. **Group administrators manage units of measure** (`org.manage`). A unit's `code` is unique and fixed once any material uses it. Its `name` is always editable. Its `decimals` may be raised at any time and lowered only while no material uses it. A unit is never deleted. A new `is_active` flag (expand migration, default true) withdraws a unit from the choices for new materials and from imports, while existing materials keep it. The seeded units stay. *Implemented in M10.3:* `catalog.services.create_unit` and `update_unit` (`org.manage`, audited as `unit.created` and `unit.updated`, the unit's row locked `FOR UPDATE` by `update_unit`), the screens on `/catalog/units/`, and `catalog.0004` adding `is_active` (expand, reversible). "In use" is worked out from the model's reverse relations (`selectors.unit_in_use`): a material, a request line or its as-submitted copy, an order line, so a free-text line that has the unit also fixes its code and decimals, and a table that later gets a unit is counted with no one editing the rule. A code is kept upper-case and unique ignoring case. An inactive unit leaves the material form and `import_catalog` (an import row that keeps a material's own inactive unit is fine, a new choice of it is refused); the free-text lines of a request still offer every unit. The check is a reading, not a lock on the documents: a line saved in the same instant as a lowering of `decimals` is not held up, because the foreign keys are checked at commit and a line reads its unit without a lock. Warehouses and worksites need no new rule: `locations.services.update_location` already refuses the branch's default warehouse, and the worksite dialogs on the project page and the warehouse list call it.
6. **A group administrator corrects a person's full name** on the person's page (ADR-0029, point 5), staff and superuser accounts excepted. A name is neither authority nor an address, so one's own name is allowed too. *Implemented in M10.4:* `accounts.services.rename_user` (`org.manage`, the user rows locked as for any account change, `require_may_manage_account`, whitespace collapsed, required, at most 150 characters, audited as `user.renamed` with the old and new name, nothing written when the name does not change) and an inline dialog on the person's page (`org:rename_person`). A rename takes no access away, so the recovery replay ignores it: a restore brings the old name back.
7. **Operator work stays on the command line**, for the maintainer on the server: `bootstrap_admin` (before any account exists), `post_restore_reconcile`, `confirm_account` and `outbox_quarantine` (recovery), `reencrypt_mfa` (key rotation), `reset_mfa` (break-glass), the bulk imports (for now; an upload screen is a separate decision), and the deploy and recovery scripts. Django's `changepassword`, which writes no audit event that a restore could replay, is disabled like `createsuperuser`.

## Alternatives rejected

- **Keep the admin as the master-data screen and widen the allowlist.** The work would still be outside the app's gates, and the allowlist exists because the admin is a privileged surface. Widening it undoes what the allowlist protects.
- **Remove the admin altogether.** Being able to inspect any record read-only helps the maintainer, and keeping it on in development and tests keeps those read-only pages tested. Off by default in production costs nothing.
- **Leave the admin editable for platform operators only.** Platform operators hold no business authority; nothing is authorized with `is_superuser`.

## Consequences

- [ADR-0004](0004-session-auth-allauth-mfa.md)'s admin bullet now says this. Plan §5 "Django Admin" carries the same amendment.
- The deploy rules of [ADR-0012](0012-maintenance-gate-deploys-recovery.md) and [ADR-0017](0017-signed-release-facts-and-public-image-packages.md) (`deploy.sh`, `ops/checks.py`) change to require the allowlist only while the admin is on. Those ADRs are updated with that change, and `docs/security.md`'s admin section and exception X10 are rewritten.
- Group administrators no longer edit master data in the admin, even when it is on: catalog and supplier screens already exist, and the rest arrive with these screens.
- Every new screen gets its rows in the access acceptance matrix, and its pages pass the browser, accessibility and keyboard tests like any other.
- The `Governs` line grows as the screens and checks land: the new views and services, `apps/core/checks.py` for the check, the settings switch.
