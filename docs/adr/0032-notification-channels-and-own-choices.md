# ADR-0032: Notifications: channels and the person's own choices

- **Status:** Accepted (the maintainer's requirement and decisions of 2026-11-19, issue #75, Q93–Q100; implemented in the M17 pull request). Amends [ADR-0031](0031-business-email-notices-set-by-administrators.md) §2, §3, §4 and §5
- **Date:** 2026-11-22
- **Governs:** `apps/notifications/in_app.py`, `apps/notifications/housekeeping.py`, `apps/notifications/services/own.py`, `apps/notifications/services/common.py`, `apps/notifications/services/reading.py`, `apps/notifications/inbox_views.py`, `apps/notifications/dialogs.py`, `apps/notifications/forms.py`, `apps/notifications/templatetags/notice_tags.py`, `apps/notifications/kinds.py`, `apps/notifications/models.py`, `apps/notifications/resolution.py`, `apps/notifications/notices.py`, `apps/notifications/selectors.py`, `apps/notifications/services/preferences.py`, `apps/notifications/views.py`, `apps/organizations/views/notification_screens.py`, `tests/e2e/test_notification_channels.py`

## Context

After ADR-0031 a person had one all-or-nothing switch (*no business email*) and read, without changing it, what the group administrators set for them; an administrator's *always* or *never* was final below that switch. At the review of that work the maintainer asked for more (issue #75): each person chooses, per business notification and per channel, what they receive; a second channel joins email, notifications **in the application** (a bell with the unread count and a list); and the person's explicit choice wins over the administrators in both directions. The planned Telegram bot is a third channel later, invisible until its own plan is done.

## Decision

1. **A registry of channels.** `apps.notifications.kinds.CHANNELS` lists the channels the installation offers, each with its default and whether it is opt-in: `EMAIL` and `IN_APP`, both on by default and not opt-in (Q96). The resolution, the services, the forms and the screens loop over it, so a channel joins by adding a value and its entry, with no new column or screen shape. Nothing of Telegram exists yet: no value, column or string (Q95). Security mail and supplier dispatches stay email only, carry no notice and are never filtered (ADR-0031 §1, ADR-0024).
2. **Four levels, in this order, per person, notice and channel** (Q93; `apps.notifications.resolution`, still one query for `wanted`/`filter_wanted`, and `decisions` saying which level decided):
   1. the person's **switch for the channel**: off, nothing reaches them there. Email's is still `NotificationPreference.email_opt_out` (expand only: the previous release reads and writes it); every other channel's is a `ChannelSwitch` row (one per person and channel, a CHECK keeps email out), and without one the channel's default;
   2. the person's **own choice** for the notice on that channel (`NoticeChoice`, on or off): it wins over both administrators' levels, **in both directions**: an own *on* beats an administrator's *never* or an *off* for everyone, an own *off* beats an *always*. No row means: follow the administrators;
   3. an administrator's **setting for the person** (`NoticeSetting`, `ALWAYS`/`NEVER`, now per channel);
   4. the **setting for everyone** (`NoticeDefault`, per channel); no row means the channel's default.

   The administrators' settings become the defaults of whoever has not chosen; choosing *as the administrators set it* deletes the person's row and brings them back. Everything stays within eligibility: email is checked again at the claim (`eligibility.eligible_recipients`, unchanged), and an in-app row at every display (§4). This replaces ADR-0031 §3, under which the administrator's setting was final below the person's switch.
3. **Who changes what** (amends ADR-0031 §4). The person changes only their own rows: `set_own_channels` (email's case is still `set_email_opt_out`) and `set_own_notices` take the principal and no user id, so no other person can be named; any current member (`catalog.view`, held by every role), with session MFA for a privileged role, as every write. The group administrators keep `set_notice_default` (one channel), gain `set_notice_channels` (one notice on every channel, in one transaction), and `set_person_notices` now takes modes keyed `(notice, channel)`, so the person's section saves one channel's table in one transaction and one event. Every service follows the write order of plan §4.7 (authorize in the transaction, idempotency record bound to the payload, which names the channel; the users locked `FOR NO KEY UPDATE`; rows `FOR UPDATE`), writes and audits only what differs from what is stored (a save that changes nothing writes nothing), and records `notification.own_changed`, `notification.default_changed` or `notification.person_changed` with before and after, branchless. Nobody is told of a change. Before M17, `set_email_opt_out` recorded `notification_preference.changed`; those events stay readable in the audit viewer.
4. **In-app notifications** (Q94, Q98, Q99). `InAppNotification` stores no text: the person, the notice, the request it is about (`kinds.SUBJECT` and its id), `notified_at` by the database clock and `read_at`. `in_app.notify` writes one row per recipient the email would have (the same `recipients`, the same capability) who wants the notice on `IN_APP`, inside the publishing service's transaction, so a rolled-back change leaves none; a reviewer's edits (`GROUPED_IN_APP`) refresh the person's unread row about that request instead of adding one (a partial unique index keeps one). Every read and every change goes through `in_app.visible(ctx)`: the person's own rows **whose request they may still see with the notice's capability**, decided inside the query (`visible_to`), so a row whose request left their scope is neither shown nor counted, and anything else (another person's row included) is a 404. The bell's count is a fragment (GET only, `@session_passive`, polled every 60 s, *99+* at most); the list is paged in the database (ADR-0023); opening one and *mark all as read* are POST-only, idempotent by nature, and **not audited**: reading one's own notifications changes nobody's access or data. A group administrator sees a person's choices, never their notifications.
5. **The purge** (Q98). The worker's housekeeping task `in_app_notifications` deletes, in batches of `PURGE_BATCH` rows within `PURGE_BUDGET` seconds per run (`DELETE … WHERE <rule> AND id IN (SELECT … LIMIT n)`; under the worker each batch is a transaction of its own, a *batched* housekeeping task, so no long lock is held, and the rule stated again on the row leaves one that a concurrent edit refreshed while the DELETE waited), the rows read more than `IN_APP_READ_RETENTION` days ago (30), those unread for `IN_APP_UNREAD_RETENTION` days (90), those beyond a person's `IN_APP_MAX_PER_PERSON` newest (200), and every row of a person offboarded `IN_APP_READ_RETENTION` days ago; durations from `config/env.py` helpers. It logs a count per rule, never who. Growth is limited at the source too: no row for who does not want it, one unread row per request for grouped edits.
6. **Screens** (Q97; amends ADR-0031 §5). *My notifications* (`/account/notifications/`): **1. Where you are told**, a switch per channel; **2. What you are told**, a row per notice and a column per channel, each cell saying whether it is sent and which level decided (and where the person's choice overrides the administrators), a column greyed while its channel is off, the notices the person's roles never receive marked; each part changes in an inline dialog posting to its own POST-only URL (one per channel for the choices). The header's bell links to `/notifications/`. *Administration › Notifications* (renamed from *Email notifications*; the URL name `org:notifications` kept) and the person's section take the same shape, notice × channel, the person's section showing, read-only, the person's own choices and where they override the administrators', with a dialog per channel. Every dialog follows ADR-0027.
7. **Restores and backups.** The settings, the choices and the in-app rows are business data, kept by backups. A restore brings back the snapshot's rows; nothing leaves the system through them, so nothing is quarantined, and none gives or takes access or a credential, so `apps.recovery.replay.HANDLERS` gains no handler (ADR-0016).

## Alternatives rejected

- **The administrator's *never* stays final** (ADR-0031 §3). The maintainer decided the person's explicit choice wins in both directions (Q93): administrators set defaults for who has not chosen.
- **A column per channel on `NotificationPreference`.** Each new channel would add a column and a migration; a `(user, channel)` table adds a value. Email's switch stays where the previous release reads it.
- **One table for the administrator's and the person's settings.** Going back to *follow* would erase the administrator's setting; two tables keep both.
- **Browser push (Web Push).** A service worker, VAPID keys, outbound calls to the browsers' push services and a permission prompt, for notifications seen while the application is closed: backlog B16, a later channel of the same registry.
- **Storing the notification's text.** A person who lost access to the request would keep reading it; drawing the row when shown, from the request as they may see it now, leaves nothing readable.
- **Auditing reads.** Opening one's own notification changes no data and no access; auditing it would grow the append-only audit table with every click.

## Consequences

- [ADR-0009](0009-no-redis-database-cache-outbox.md): the outbox and its claim are unchanged; the in-app channel writes no outbox row and sends nothing. Checked, still holds.
- [ADR-0016](0016-restores-hold-what-can-hand-over-an-account.md): no new replay handler (§7). Checked, still holds.
- [ADR-0023](0023-lists-page-in-the-database.md): the list pages in the database; the list and the bell are `Screen`s of the volume test. Checked, still holds.
- [ADR-0024](0024-session-idle-limits-own-sessions-credential-notices.md): security mail never carries a notice; the bell's poll is `@session_passive`, so it never counts as activity. Checked, still holds.
- [ADR-0027](0027-ui-design-system.md), [ADR-0029](0029-people-by-name-addresses-to-managers.md), [ADR-0030](0030-administration-in-the-app.md): the screens use the dialog contract and the components, show people by name, and the new models are read-only in the admin with their inventory rows. Checked, still hold.
- Release: migrations `notifications.0007` (`NoticeChoice`, `ChannelSwitch`) and `notifications.0008` (`InAppNotification`) only add tables, so the previous release runs on the new schema; shipped in one 0.Y.0 with M15 and M16 (Q100).
- A later channel (the Telegram bot) adds a `Channel` value and its `CHANNELS` entry (opt-in), its account link and its sender; the levels, the services and the screens take it as they are.
